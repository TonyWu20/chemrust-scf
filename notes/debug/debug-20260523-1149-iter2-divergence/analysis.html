h_eig vs prior eigenvalues — what Mode B is getting wrong

Session: debug-20260523-1149-iter2-divergence
Goal: explain the technical distinction between h_eig (what production currently uses) and the prior-iteration generalized eigenvalues (what Das Algorithm 3 specifies), and why this matters at iter-2.

1. The two quantities, defined

1a. h_eig — per-band Rayleigh quotient on bare H

Computed fresh inside the filter, once per call, at chebyshev.rs:1509-1538:

h_eig[b] = ⟨ψb | H | ψb⟩

This is a property of the current input ψ (the wavefunction passed into the filter). It depends on whatever ψ looks like right now, including any pollution or residual mixing of eigenvectors.

If ψb is an exact eigenvector of bare H with eigenvalue λb, then h_eig[b] = λb. If ψb is a mixture of eigenvectors, h_eig[b] is a weighted average of their eigenvalues (the Rayleigh quotient identity).

1b. Prior generalized eigenvalues — eigenvalues[] from RR

Passed into the filter via the eigenvalues: Option<&[f64]> argument. Originates from the prior iteration's Rayleigh-Ritz step (scf.rs:553), where ZHEGVD solved the generalized eigenproblem:

Hsub · X = λgen · Ssub · X

These λgen are eigenvalues of the operator S−1·H projected onto the iter-1 subspace. They are frozen at the moment the prior iteration finished, independent of the current ψ being filtered.

3. What Das Algorithm 3 actually says

From reference_paper/extracted/das-2025-rchfsi/main.tex lines 595-606, the INPUTS to Algorithm 3 explicitly include:

"current eigenvalue estimates Λ(i) = diag(ε₁(i), …, εₙ(i))"

The superscript (i) denotes the prior outer iteration. Concretely Λ(i) are the eigenvalues from the previous Rayleigh-Ritz solve — i.e. eigenvalues[] passed into our filter, not h_eig.

Algorithm 3 then uses Λ(i) in two places:

Line 597: Y ← A·X(i) − B·X(i)·Λ(i)   (residual definition)
Line 598: Λ_Y ← (σ₁/e)·(Λ(i) − c·I)   (initial Λ_Y)
Line 599: Λ_X ← (2σ₂/e)·Λ_Y·Λ(i) − (2σ₂/e)·c·Λ_Y − σ·σ₂·Λ_X   (recurrence Λ_X update)

All three uses of Λ(i) reference the same quantity — the prior iteration's eigenvalues.

4. What Mode B actually does (the bug)

Lines chebyshev.rs:1578-1581 set the source for Λ(i):

let lam_source: &[f64] = match filter_mode {
    FilterMode::SinvHFullDas => eigenvalues.unwrap_or(&h_eig),
    _ => &h_eig,           // <-- Mode B always uses h_eig, ignoring eigenvalues
};

Mode B (production default) hits the catch-all arm and ALWAYS uses h_eig — even when eigenvalues contains the correct prior iteration data.

Mode C (SinvHFullDas) does the right thing: uses eigenvalues when available, falls back to h_eig only when none provided.

The bug: Mode B uses Rayleigh quotients of bare H on the current input ψ as a proxy for prior-iteration generalized eigenvalues. These quantities only agree when ψ is exactly an eigenvector of S−1·H. Once ψ drifts (iter-2 V_eff change, pollution, or any other perturbation), h_eig and the true Λ(i) diverge, and Mode B's recurrence is fed wrong shift values.

Both of those branches use lam_source, which for Mode B is hard-wired to &h_eig at line 1580. So the per-band shifts being applied use Rayleigh quotients of the polluted ψ rather than the prior iteration's true generalized eigenvalues.

5b. Why iter-1 succeeded despite this bug

Iter-1 has eigenvalues = None (no prior RR yet). The branches at chebyshev.rs:1582-1587 and 1652-1660 take the simpler path (uniform scalar shift, no per-band coeff·ly·l term). The bug is gated behind is_some(), so iter-1 doesn't trigger it.

5c. Why production iter-2 cascade

At production iter-2:

  1. ψ = iter-1's RR output, S-orthonormal generalized eigenvector basis
  2. V_eff slightly different from iter-1's because ρ changed
  3. So h_eig[b] = ⟨ψb|Hnew|ψb⟩ ≠ λgen,b (the iter-1 RR eigenvalue)
  4. Mode B feeds h_eig as Λ(i) into the recurrence (line 1580)
  5. Per-band shifts at line 1583 and 1654 use slightly-wrong Λ(i)
  6. Recurrence amplifies the wrong eigencomponents over 8 steps
  7. Last band drifts from 0.13 Ha to 1.95 Ha
  8. Iter-3 uses 1.95 Ha as b_low, filter window collapses, cascade explodes

6. Proposed fix

Change line 1580 of chebyshev.rs: 
let lam_source: &[f64] = match filter_mode {
    FilterMode::SinvHFullDas => eigenvalues.unwrap_or(&h_eig),
-   _ => &h_eig,
+   _ => eigenvalues.unwrap_or(&h_eig),
};

With this change, Mode B falls back to h_eig only when no prior eigenvalues exist (iter-1 path), and uses the passed-in eigenvalues for iter-2+.

7. Risk: will this break iter-1 SC-4-tight?

§10's filter-mode sweep showed Mode B winning iter-1 SC-4-tight with all 10 bands within 0.05 Ha, while Mode C lost by 10× (band-0 |ΔC| ≈ 0.13 Ha).

Crucially, at iter-1 the proposed fix changes nothing: eigenvalues is None on the iter-1 call, so eigenvalues.unwrap_or(&h_eig) = &h_eig. Mode B's behavior at iter-1 is unchanged.

The fix only changes behavior when eigenvalues.is_some() — i.e. iter-2 and beyond. So iter-1 SC-4-tight should remain green.

Mode C lost iter-1 not because of the lam_source choice (Mode C also gets None at iter-1 → falls back to h_eig identically to Mode B). Mode C's loss came from the extra apply_s_inverse in Step 4 reconstruction (chebyshev.rs:1693) plus possibly other Mode-C-specific differences. The proposed fix doesn't touch that line.

8. Verification plan

Before changing production code:

  1. Add a test flag that toggles the lam_source choice independently of filter_mode. Re-run the bisecting probe with the flag forcing lam_source = eigenvalues for Mode B.
  2. If Δ_band0 drops back to ~0.00016 Ha (Trial 0 value), the hypothesis is confirmed and the fix should be applied to production.
  3. If Δ_band0 stays elevated, the bug is elsewhere in branches 2+3 (perhaps a sign error in the formula at line 1583 or 1654 itself, not just the source).
